# Изменения

Одна папка = одно изменение (эпик или самостоятельная задача). Содержание живёт здесь,
статусы — в Jira; ни то ни другое не дублируется.

## Структура

    docs/changes/
      _template/               шаблоны intent.md и plan.md
      <KEY>/                   ключ из Jira (BUIP-1234); слаг допустим только для
                               черновика, до появления ключа
        intent.md              зачем — гейт 1, принимает владелец продукта
        plan.md                как — гейт 2, принимает человек; при отклонении
                               реализации правится в том же коммите
        tasks/<slug>.md        спеки задач, если изменение нарезано; имя файла — слаг
                               без ключа, ключ — в шапке файла; префикс a-/01- только
                               когда важен порядок
        assets/                снимки: наблюдаемые контракты, экспорт макетов

Выбор между вариантами не описывается ни в intent, ни в plan — он оформляется ADR в
`docs/decisions/` (критерии там в README); intent и план ссылаются на номер.

## Связка с Jira, ветками и MR

- Jira-задача: цель, критерии приёмки, зависимости и строка
  «Спека: docs/changes/<KEY>/…». Подробности — только в файле; изменение требований =
  правка файла через MR, не правка описания в Jira.
- Один тикет = одна спека = один MR **реализации**. MR плана — отдельный, документный:
  это гейт, а не работа.
- Ветка `feature/<KEY>` — GitLab слинкует MR с Jira сам.
- Статусы не смешивать: жизненный цикл задачи — владелец Jira; статус документа
  (draft / accepted / superseded / done) — шапка файла.

## Жизненный цикл: что появляется и что становится историей

| Этап | Появляется | Гейт |
|---|---|---|
| Заведение | тикет + папка `<KEY>` | — |
| Намерение | `intent.md` (+ ADR `proposed`, если есть развилка) | владелец продукта: intent → `accepted` |
| План | `plan.md` через документный MR | человек аппрувит MR: plan → `accepted` |
| Реализация | код; при отклонении план правится в том же коммите | verify зелёный на каждом шаге |
| Ревью | MR реализации: хвост verify, смоуки; повторная ошибка агента → строка в AGENTS.md | CI → AI-ревью → человек: то, что просили? риски закрыты? тесты не ослаблены? |
| Merge | — | intent/plan → статус `done` |

После merge истина переезжает: ей становятся код, тесты, правила линтера, справочники
(`AGENTS.md`, `ARCHITECTURE.md`, `docs/nitro3/`) и ADR — их правка входит в MR реализации,
не «потом». `intent.md` и `plan.md` остаются историей: не поддерживаются, не удаляются.

Проверка закрытия: новый человек или агент получает полную правду о системе из вечного
слоя, не открыв ни одного `docs/changes/`. Если для понимания нужно читать старый план —
знание не переехало в справочник, это дефект закрытия.

## Пороги

- Изменение дольше ~2 часов — папка с `intent.md`; `tasks/` — по необходимости.
- Короче 2 часов или ≤ 20 строк без изменения публичного API — без папки: Jira + MR.

## Агенту

Задача выдаётся как путь к файлу спеки; `AGENTS.md` читается всегда. Спека самодостаточна:
если для работы нужно что-то сверх неё и справочников `docs/` — это дефект спеки, чинится
правкой файла через MR, а не устным уточнением. Сводного реестра изменений нет намеренно:
список = содержимое папки, статусы = Jira.
