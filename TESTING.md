# План тестирования прототипа

Принцип: каждый фейл — вход в улучшение пакета (патч схемы, правило, пример,
семантическая проверка). Все изменения фиксируются в README-чейнджлоге, после
исправлений — повторный прогон. Этапы идут по порядку: каждый следующий опирается
на подтверждения предыдущего.

## Э1. Стенд: рецепт запуска произвольного конфига (~полдня)

Действия: `nitro3:serve` с файлом конфига (уже умеет). Интерсепторы НЕ пишем:
вся подмена сети — на стороне проверяющего браузера, `tools/sandbox.mjs`
(Playwright route mocking). Смоук: `node tools/sandbox.mjs <url> --mocks <file>`
(headless, ошибки консоли/сети, скриншот, код выхода); ручная приёмка — то же
с `--headed`. Один раз: `npx playwright install chromium`.

Подтверждаем: произвольный YAML поднимается изолированно; КЛЮЧЕВОЕ — перечитывает
ли serve файл конфига на перезагрузке страницы без пересборки (скорость
repair-цикла агента). Формат mocks-файла — единый контракт фаз (см. шапку
sandbox.mjs): сейчас его ест Playwright, в Ф1 — config-стаб контейнера,
в Ф2 — секция mocks конфига.
Чиним: если serve требует пересборку на смену конфига — маленькая правка serve
(читать конфиг статикой по URL), это единственное изменение фронта, которое
может понадобиться.

## Э2. Пробы поведения (`runtime-checks/`) (~полдня)

Три конфига, каждый сам печатает ответ на экран:
- `probe-model-init` — эмитит ли модель `state` при инициализации;
- `probe-outputs-context` — жив ли баг localBindings outputs + context/condition
  (рядом контрольный глобальный биндинг);
- `probe-setinputs-echo` — эмитит ли `setInputs {text}` событие `text`
  (риск петель и каскадов).

Подтверждаем: три факта поведения, на которых стоят правила README.
Чиним: правила 1/6 и примеры по фактам; при живом баге — issue платформе
(репро уже готов файлом).

## Э3. Прогон эталонов 01–12 на стенде (~день)

По каждому примеру: поднялся; консоль чистая; 2–4 действия из шапки файла работают.
Точечные допущения к подтверждению:
- 04 — формы `success.body` / `failure.status|body` / `inProgress` (замокать
  `/demo/api/profile/get`: успех с задержкой и 500);
- 05/06 — доставка `inputs` презентера при инициализации и через setInputs;
  перерендер динамических списков (поведение после reconcile-доработок);
- 07 — `urlState.pathSegments`, `navigate {commands}`, работа с baseHref;
- 08 — всплытие `click` с `meta` до menuGroup; вход `open` у dropdown;
- 10 — заменить URL-заглушку на реальный лёгкий МФ (например, твой
  chat-mf-simulation) и проверить mfInput/mfOutput;
- 11/12 — семантика KeyValue/Spread в рантайме; формы `tick.timePassed`
  и `isStarted` (сверялись по типам и конвертеру, не в рантайме).

Подтверждаем: эталоны — истинные (им будет верить агент).
Чиним: примеры и правила; расхождения полей/событий → кандидаты в схему.

## Э4. Калибровка валидатора на реальных конфигах (~полдня–день)

Действия: выгрузить конфиги приложений из конфигли (ручки видны в каноне:
`get-my-list` → `configuration/version/get`; могу написать скрипт выгрузки —
нужен способ авторизации) и прогнать всё через `npm run validate`.

Подтверждаем: доля прохождения реального прода; список полей, которых схема
не знает (особенно после strict `menuGroup` и новых required у localBindings).
Чиним: каждый false positive — патч схемы; спорные места (strict vs permissive) —
твоё решение, фиксируем в чейнджлоге.

## Э5. E2E агента (~1–2 дня)

5.1 Транспорт, 1 задача: заголовок авторизации (как есть vs `Bearer`), актуальный
id модели Claude в личном кабинете прокси, прохождение tool_use через прокси и —
отдельно — не корёжит ли анонимизация прокси YAML в аргументах инструментов
(русские строки, URL). При маскировании — согласовать исключения для проекта.

5.2 Прогон `eval/tasks.md` (9 задач, формулировки дословно). Метрики и порог —
в шапке файла: ≥7/9 поднимаются, ≥5/9 проходят приёмку без правок. Первый прогон —
калибровка, не экзамен.

5.3 Разбор фейлов по классификации (а) схема / (б) правило-пример /
(в) семантическая проверка / (г) промпт-модель → патчи → повторный прогон.
Именно этот цикл и есть развитие прототипа.
